# partition — разбиение двудольного графа воркер–задача

Пакет делит большой взвешенный двудольный граф (воркеры ↔ задачи, вес ребра —
скор в `[0, 1]`) на сабграфы, каждый из которых не превышает лимит рёбер и
может быть отправлен в матчмейкинг независимо.

Два режима:

| Режим | Что уникально | Что с рёбрами через границу |
|---|---|---|
| `EdgeCut` | и воркеры, и задачи — ровно в одном сабграфе | исключаются из тика, возвращаются в `Result.Cut` |
| `UniqueTasks` | задачи — ровно в одном сабграфе; воркер копируется во все сабграфы, где есть его задачи | не теряются |

Оба режима — один и тот же конвейер, отличаются только тем, какие вершины
двигает уточнение разреза и как считается его стоимость.

---

## 1. Постановка

- Вход: список рёбер `(Task, Worker, Score)`. Граф не обязан быть связным.
- Выход: сабграфы по `≤ MaxEdges` рёбер.
- Цель: минимизировать «цену разреза» при сбалансированном числе рёбер.
  - `EdgeCut`: Σ скоров отброшенных рёбер.
  - `UniqueTasks`: Σ скоров *гостевых копий* воркеров. Домашняя партиция
    воркера — та, где Σ скоров его рёбер максимальна; всё, что ушло в
    другие партиции, — стоимость.
- Требование: детерминизм. Один и тот же набор рёбер в любом порядке даёт
  байт-в-байт одинаковый результат. Это нужно, чтобы задача не «прыгала»
  между партициями от тика к тику.

Граф целиком помещается в память планировщика (он уже прошёл DFS по
компонентам), поэтому стриминговые алгоритмы (Fennel/LDG) не используются —
они жертвуют качеством ради однопроходности, которая здесь не нужна.

## 2. API

```go
type Edge struct {
    Task, Worker uint64
    Score        float32 // ожидается в [0, 1]
}

type Config struct {
    Mode     Mode    // EdgeCut | UniqueTasks
    MaxEdges int     // лимит рёбер на сабграф, > 0
    Theta    float32 // рёбра со Score < Theta отбрасываются до разбиения; 0 = без прунинга
    Epsilon  float64 // допуск баланса бисекции, по умолчанию 0.1
    FMPasses int     // проходов уточнения, по умолчанию 3; <0 = без уточнения
}

type Part struct {
    Edges          []Edge
    Tasks, Workers int // число различных задач / воркеров
}

type Result struct {
    Parts     []Part  // сабграфы, каждый с ≥ 1 ребром
    Cut       []Edge  // EdgeCut: отброшенные рёбра; UniqueTasks: пусто
    CutCost   float64 // цена разреза (см. §1)
    Pruned    int     // рёбер удалено прунингом и дедупликацией
    Oversized int     // сабграфов > MaxEdges, которые нельзя разбить (§6)
}

func Partition(cfg Config, edges []Edge) Result
```

Дубликаты `(Task, Worker)` схлопываются, остаётся максимальный скор.

```go
res := partition.Partition(partition.Config{
    Mode:     partition.UniqueTasks,
    MaxEdges: 20000,
    Theta:    0.1,
}, edges)

for _, p := range res.Parts {
    go matchmaker.Submit(p.Edges) // независимо
}
```

## 3. Конвейер

```
рёбра → прунинг θ → CSR → компоненты связности
                              │
                   ┌──────────┴──────────┐
              ≤ MaxEdges              > MaxEdges
                  │                       │
               emit                    бисекция
                                 (BFS-порядок → разрез по
                                  половине рёбер → FM)
                                          │
                                   рекурсивно на обе половины
```

### 3.1 Прунинг

Рёбра со `Score < Theta` удаляются до всего остального. Это самый дешёвый
и самый эффективный шаг: тонкие рёбра почти никогда не выигрывают матчинг,
а после их удаления большие компоненты часто распадаются сами, и бисекция
не нужна.

### 3.2 Компоненты связности

BFS внутри текущего рабочего множества. В `EdgeCut` обход обычный
(задача → воркер → задача); в `UniqueTasks` множество состоит только из
задач, а воркеры — транзитные вершины: задача → её воркеры → их задачи.
Каждый воркер раскрывается один раз (помечается штампом), поэтому воркер-хаб
с тысячами задач не сканируется повторно.

### 3.3 Бисекция

Выполняется для связной компоненты с числом рёбер `> MaxEdges`.

1. **Стартовая вершина** — максимальная взвешенная степень (Σ скоров в
   рабочем множестве), при равенстве — меньший индекс. Индексы следуют
   порядку id, это основа детерминизма.
2. **BFS-порядок** от стартовой вершины. Списки смежности отсортированы,
   обход детерминирован.
3. **Начальный разрез.** Идём по порядку и накапливаем рёбра стороны A:
   - `EdgeCut`: ребро считается, когда оба его конца уже в A;
   - `UniqueTasks`: задача приносит всю свою степень.

   Останавливаемся, когда `2·edges(A) ≥ total`. Остаток — сторона B.
   BFS-префикс связен, поэтому начальный разрез уже неплох: он режет
   «хвост» обхода, а не середину кластера.
4. **Уточнение (FM)** — см. §4.
5. Обе половины получают новые id множеств и обрабатываются рекурсивно.
   Число партиций `k` нигде не задаётся — оно получается из `MaxEdges`.

### 3.4 Сборка результата

- `EdgeCut`: ребро попадает в сабграф, если оба конца в одном регионе;
  иначе — в `Cut`. Вершины, оставшиеся без рёбер после разреза, ни в какой
  сабграф не попадают (матчить нечего).
- `UniqueTasks`: ребро попадает в сабграф своей задачи. Воркер оказывается
  во всех сабграфах, где есть его задачи. `CutCost` = Σ по воркерам
  `(Σ скоров − max по регионам Σ скоров)`.

Сабграфы нумеруются в порядке их появления в рекурсии → порядок выходa
детерминирован.

## 4. Уточнение разреза: Fiduccia–Mattheyses

Классический FM с ленивой кучей:

- Для каждой подвижной вершины считается **gain** — на сколько уменьшится
  цена разреза, если перенести её на другую сторону.
- Вершины лежат в max-куче по gain (при равенстве — меньший индекс).
  Устаревшие записи помечаются версией и пропускаются при извлечении.
- Извлекаем лучшую, проверяем баланс, переносим, **блокируем** до конца
  прохода, обновляем gain соседей инкрементально.
- Переносы с отрицательным gain тоже выполняются — так FM выходит из
  локальных минимумов. Запоминаем лучший префикс последовательности
  переносов; в конце прохода откатываем всё после него.
- Проход прекращается, если `max(32, |V|/20)` переносов подряд не улучшили
  лучший результат — хвост классического FM почти никогда не помогает,
  но доминирует по времени.
- Повторяем до `FMPasses` проходов или пока проход не даёт улучшения.

**Баланс.** Перенос допустим, если после него
`max(edges(A), edges(B)) ≤ ⌈total·(0.5+Epsilon)⌉`. Если начальный разрез
уже хуже этой границы, допустимы только переносы, не увеличивающие
текущий максимум.

### 4.1 EdgeCut

- Подвижны и задачи, и воркеры.
- `gain(v) = Σ_{u ∈ N(v)} (side(u) ≠ side(v) ? w : −w)`.
- После переноса `v`: соседям на старой стороне `gain += 2w`, на новой
  `gain −= 2w`. O(deg v) за перенос.
- Счётчик рёбер стороны: `edges(from) −= #соседей на старой стороне`,
  `edges(to) += #соседей на новой`.

### 4.2 UniqueTasks

- Подвижны только задачи.
- Для каждого воркера `w` хранятся `sA[w]`, `sB[w]` — Σ скоров его рёбер
  к задачам сторон A и B. Стоимость разреза `= Σ_w min(sA[w], sB[w])` —
  ровно Σ скоров гостевых копий.
- `gain(t) = −Σ_{w ∈ N(t)} [min(sA', sB') − min(sA, sB)]`, где
  штрихованные суммы — после переноса `t`.
- После переноса `t` меняются `sA/sB` его воркеров, а значит gain всех
  *других задач этих воркеров*. Обновление инкрементальное, O(1) на пару
  (воркер, задача): вычитаем старый вклад воркера, прибавляем новый.
  Затронутые задачи собираются в список «грязных» и попадают в кучу одной
  записью каждая, а не по записи на каждого общего воркера.
- Счётчик рёбер стороны: `± deg(t)`.

Стоимость переноса — `O(Σ_{w ∈ N(t)} deg(w))`. Для воркера-хаба это
дорого, но в `UniqueTasks` хаб — именно тот случай, когда репликация
дешёвая, и ограничение на длину хвоста прохода (§4) держит время в рамках.

## 5. Параметры и как их выбирать

| Параметр | Рекомендация |
|---|---|
| `MaxEdges` | Лимит матчинга на одной машине. Для `UniqueTasks` копии воркеров увеличивают размер сабграфа: ребро задачи приносит в партицию и своего воркера, так что фактическое число рёбер = `Σ deg(task)` и лимит соблюдается точно. Для `EdgeCut` сабграф всегда ≤ лимита. |
| `Theta` | Подбирается на реальных данных: максимальное θ, при котором потеря оптимума матчинга < 1 %. Обычно 0.05–0.15. Смотреть долю компонент, которые после прунинга всё ещё > `MaxEdges`: если она близка к нулю, бисекция — редкий fallback. |
| `Epsilon` | 0.05–0.1. Больше — свободнее FM, лучше разрез, хуже баланс. |
| `FMPasses` | 2–3. Почти всё улучшение даёт первый проход. |

Метрики для мониторинга:

- `CutCost / Σ всех скоров` — доля «потерянного» (EdgeCut) или
  «продублированного» (UniqueTasks) веса. Если < 3–5 %, усложнять дальше
  незачем.
- `max |Part| / avg |Part|` — дисбаланс.
- `Oversized` — должен быть 0.

## 6. Гарантии и ограничения

Гарантируется:

- Каждая задача ровно в одном сабграфе (оба режима).
- `EdgeCut`: каждый воркер ровно в одном сабграфе;
  `Σ|Parts| + |Cut| = |E после прунинга|`.
- `UniqueTasks`: `Cut` пуст; `Σ|Parts| = |E после прунинга|`.
- Каждый сабграф `≤ MaxEdges`, кроме случаев `Oversized`.
- Детерминизм относительно набора рёбер.

`Oversized > 0` возникает, когда компоненту нельзя разделить:

- `UniqueTasks`: одна задача с `deg > MaxEdges` — её рёбра неразделимы.
- `EdgeCut`: формально разделить можно всегда (отбросив рёбра), поэтому
  `Oversized` там практически не встречается; но звезда «один воркер —
  30 000 задач» будет разрезана на сабграф ≤ лимита плюс отброшенный
  хвост рёбер.

Что алгоритм **не** делает:

- Не оптимален. Это эвристика уровня METIS/hMETIS-refinement; на
  кластерных графах находит естественный разрез (см. тесты), на
  произвольных — хороший, но не доказуемо лучший.
- Не учитывает ёмкость воркера. В `UniqueTasks` воркер с копиями в
  нескольких сабграфах может получить несколько предложений; конфликт
  разрешает сам воркер (или мягкий штраф гостевым копиям на стороне
  матчинга).

## 7. Интеграция с планировщиком (тик 5 с)

```
каждые 5 с:
  граф ← актуальная версия из БД
  res ← Partition(cfg, граф)            // компоненты + разбиение больших
  for p in res.Parts: submit(p) async   // независимый матчинг
  (EdgeCut) после матчинга:
      свободные воркеры × несматченные задачи, только рёбра из res.Cut
      → быстрый жадный матчинг в планировщике
```

Второй проход по `Cut` в `EdgeCut` стоит дёшево (рёбер разреза десятки,
не тысячи) и возвращает большую часть потерянного. Если его не делать —
ребро просто дождётся следующего тика, граф к тому моменту другой.

Время на ~100 000 рёбер (2 ядра, Go 1.24, лимит 20 000):

| Режим | мс/вызов |
|---|---|
| `EdgeCut` | ≈ 80 |
| `UniqueTasks` | ≈ 150 |

## 8. Разобранный пример

5 воркеров, 6 задач, 12 рёбер, лимит 8:

```
T1: W1 0.9, W2 0.6      T4: W3 0.8, W4 0.7
T2: W1 0.7, W2 0.8      T5: W4 0.9, W5 0.5
T3: W2 0.3, W3 0.9      T6: W4 0.4, W5 0.9
```

**UniqueTasks.** Старт — T1 (Σ = 1.5, ничья с T2, T4 → меньший id).
BFS: T1 → T2, T3 → T4 → T5, T6. Разрез после 3 задач (6 из 12 рёбер):
A = {T1, T2, T3}, B = {T4, T5, T6}. Реплицирован W3 (T3 в A, T4 в B),
стоимость `min(0.9, 0.8) = 0.8`.

FM: перенос T3 → B. W3 перестаёт быть гостем (−0.8), W2 становится
гостем в B с рёбром 0.3 (+0.3). gain = 0.5, рёбер 4/8 ≤ 8 — принято.
Итог: `{T1, T2}` + `{T3, T4, T5, T6}`, стоимость 0.3, W2 в обоих
сабграфах.

**EdgeCut.** Старт — W4 (Σ = 2.0). BFS: W4 → T4, T5, T6 → W3, W5 → T3 →
W2 → T1, T2 → W1. Разрез: A = {W4, T4, T5, T6, W3, W5} (6 рёбер),
B = {T3, W2, T1, T2, W1} (5 рёбер), разрез T3–W3 (0.9).

FM: перенос T3 → A. gain = 0.9 − 0.3 = 0.6; рёбер 7/4 ≤ 8 — принято.
Итог: разрез T3–W2 (0.3), одно ребро из 12 выпало из тика.

Оба результата зафиксированы в `TestExampleEdgeCut` /
`TestExampleUniqueTasks`.

## 10. Структура кода

```
partition.go
  Partition()            — вход: прунинг, построение CSR, запуск рекурсии, сборка
  buildGraph()           — сортировка, дедупликация, прунинг, CSR
  partitioner.process()  — компоненты → emit | bisect → рекурсия
  partitioner.bisect()   — старт, BFS, начальный разрез, вызов FM
  refineEdgeCut()        — FM для EdgeCut
  refineUniqueTasks()    — FM для UniqueTasks
  assemble()             — Parts, Cut, CutCost
partition_test.go
```

Внешних зависимостей нет. Память: CSR на `2·|E|` записей плюс O(|V|)
служебных массивов; на 1 млн рёбер — порядка 30 МБ.
